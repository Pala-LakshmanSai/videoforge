# VF-8-03 — RunPod scale-zero control adapter

Status: exact successor selected after VF-8-02

## Goal

Build the server-only RunPod control adapter that every locked GPU lane must use, prove account and
resource visibility live, and make zero-idle cleanup a fail-closed invariant before any model worker
is deployed.

## Context read profile

Use `phase8_runpod_scale_zero` from `MANIFEST.yaml`.

## In scope

- Load the existing RunPod key only from macOS Keychain.
- Add typed, redacted RunPod API transport for account, Pods, Serverless endpoints/templates,
  dispatch/status/cancel, and delete/drain reconciliation.
- Enforce `workersMin=0`, `workersMax=1`, one bounded worker lane, immutable request identity,
  timeout, ambiguity, cancellation, and confirmed zero-resource shutdown.
- Fake-transport tests cover auth, replay, cap/config rejection, ambiguous mutation, drain/delete,
  secret redaction, and refusal to dispatch when cleanup state is uncertain.
- Perform only live read-only account/resource inventory. Do not start compute in this task.

## Authority and limits

- RunPod API access is authorized using only Keychain service `com.videoforge.runpod.lifecycle`,
  account `videoforge`; never print or persist the value.
- Maximum new external spend: `$0.00`.
- No Pod start, Serverless worker start, endpoint/template creation, volume creation, model/weight
  download, deployment, push, or non-RunPod provider call.

## Acceptance

- Live evidence records balance and counts/IDs only in redacted/hash form and proves no active paid
  compute was created by the task.
- Adapter cannot represent `workersMin>0`, `workersMax>1`, dispatch during uncertain cleanup, or a
  successful drain without provider confirmation.
- Focused tests, `pnpm verify:fast`, context/schema validation, secret scan, dependency audit,
  Prettier, and `git diff --check` pass; server stopped at handoff.
- Evidence: `evidence/acceptance/VF-8-03/runpod-scale-zero`.
