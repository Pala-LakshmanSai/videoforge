# VF-1-01 — durable relational foundation

Status: ready for implementation
Milestone: Phase 1 durable control-plane foundation
Owner: next-chat integration owner
Read profile: `phase1_foundation`

## Outcome

Create the provider-free relational foundation that every later durable adapter can share: one
`@videoforge/control-plane` package containing committed additive PostgreSQL migrations,
query-library-neutral repository contracts, and an executable PGlite migration/constraint contract
suite. Do not connect to Neon, deploy Cloudflare resources, add authentication, or change visible
fixture/local behavior in this task.

The task is complete only when a fresh in-memory PostgreSQL database can apply the full migration
chain, the critical tenant/idempotency/immutability/ledger invariants are exercised, the repository
contracts express the required atomic operations, and the existing application remains green.

## Dependencies and fixed decisions

- Phase 0A, the accepted Phase 0B shell, and the accepted Phase 0C local walking slice are complete.
- Start from the clean current `main` HEAD. It must descend from
  `CURRENT_STATE.yaml.repository.verified_implementation_commit`; never reset or check out that
  older evidence commit over newer context-only handoff commits.
- `DEC_HOSTING_001`: production relational truth is Neon Postgres.
- `DEC_QUEUE_001`: Postgres is authoritative; provider queues are transports.
- `DEC_DB_001`: committed additive SQL migrations and repository contracts are authoritative;
  PGlite is a test/dev dependency only; the Neon driver and production query implementation are
  deferred to `VF-1-02`/`VF-1-05`.
- `DEC_CONTRACT_001`: TypeScript remains the only RFC 8785/JCS authority.
- No open model/provider gate is required because this task is local, deterministic, and `$0`.

## Exact scope

### New package

Create `packages/control-plane/` with the normal workspace package shape:

- `package.json`, TypeScript configs, README, lint/typecheck/test/build scripts.
- `migrations/0001_durable_control_plane_foundation.sql` and a deterministic migration manifest.
- `src/database/**` for migration metadata/executor contracts and relational vocabulary.
- `src/repositories/**` for domain-oriented repository and transaction interfaces.
- `tests/**` for migration, constraint, and reusable repository-contract suites.

The package may use the current stable `@electric-sql/pglite` as a development/test dependency.
Pin the exact resolved version in the lockfile. Do not add Drizzle, another ORM/query builder, a
Neon driver, Docker, or a database service in this task. Future production adapters must be able to
implement the repository interfaces without changing their semantics.

### Relational record groups

The first additive migration covers the records already defined in
`10_DATA_AND_API_CONTRACTS.md`:

1. Identity: `users`, `workspaces`, `memberships`.
2. Avatar presets: `avatar_profiles`, `avatar_profile_versions`, `avatar_profile_assets`,
   `avatar_compatibility_assessments`, `avatar_profile_test_attempts`.
3. Image styles: `image_styles`, `image_style_versions`, `image_style_references`,
   `image_style_analysis_attempts`, `image_style_previews`.
4. Projects/editorial truth: `projects`, `project_inputs`, `project_revisions`, `transcripts`,
   `transcript_words`, `timeline_segments`.
5. Durable execution: `execution_profiles`, `generation_tasks`, `attempts`, `assets`,
   `qa_results`, `render_jobs`, `cost_events`, `workflow_events`, `workflow_instances`, `outbox`.

Large canonical documents remain JSONB/object-storage payloads with explicit contract name/version,
asset ID, and SHA-256 columns. Do not decompose every schema field into mutable columns or duplicate
resolved revision fields in `project_inputs`.

### Database representation rules

- Use native UUID primary keys for durable internal identities and text only for external/provider
  IDs, immutable contract names, hashes, and object keys.
- Use `timestamptz` in UTC. Timeline boundaries remain integer frames/milliseconds, never floating
  seconds.
- Store money as nonnegative integer micro-USD plus explicit `USD`; never use floating-point money.
- Every workspace-owned record carries `workspace_id`. Composite foreign keys or equivalent
  constraints must reject cross-workspace parent/child binding.
- Prefer text plus checked state vocabularies over hard-to-evolve PostgreSQL enum types.
- Use soft archive/terminal state for user data. Do not cascade-delete immutable revisions,
  attempts, assets, events, costs, or accepted provenance.
- Use partial unique indexes for one active name/open draft/accepted result where applicable.
- Store canonical JSON/document hashes and binary hashes distinctly; never recompute JCS in SQL.
- Migrations are append-only and committed. Verification may apply them; it must never use a
  schema-push command that mutates an external database.

### Repository contracts

Expose narrow domain operations, not generic unscoped CRUD. At minimum define contracts for:

- identity/workspace membership and authorization lookup;
- avatar/style parent-version publication and immutable exact-version resolution;
- project shell/input verification and immutable revision creation;
- artifact metadata and workspace-scoped content-address binding;
- atomic task + attempt + cost reservation + outbox creation;
- execution claim, dispatch-ack-unknown, reconciliation, cancellation, and one accepted result;
- append-only monotonic workflow events and cost events;
- transaction/unit-of-work execution with typed conflict/not-found/invariant results.

Every method takes an explicit workspace scope. Externally billed or retryable mutations take a
deterministic idempotency key. Contracts must make it impossible to mistake provider acknowledgement
for accepted completion.

## Required invariants and tests

Run the migration and repository suites against a new PGlite database per test group. Prove at
least:

- an empty database applies the migration chain and a second migration run is a no-op;
- the expected table/index/foreign-key inventory exists;
- normalized active user/preset names cannot duplicate within one workspace but may repeat across
  workspaces;
- cross-workspace membership, preset version, project revision, asset, task, and attempt bindings
  fail;
- one profile/style has at most one open draft and an active pointer cannot target another parent;
- ready/published version payload identity is immutable through the repository contract;
- a revision snapshots exact avatar/style/runtime-source/config hashes and cannot mutate after lock;
- task/attempt/outbox idempotency keys reject duplicate cost-producing reservations;
- event sequence is unique and monotonic per aggregate/attempt;
- cost amounts cannot be negative and owner type/ID is always present;
- one task can have only one accepted result while duplicate attempts remain visible;
- a failed transaction leaves no orphan attempt, reservation, or outbox row;
- archive never destroys historical revision/attempt/asset lineage.

Export the repository contract suite so the later PGlite/Neon implementations must both pass the
same behavior. Tests must use owned synthetic IDs/data and no network.

## Commit and parallel execution plan

The integration owner controls `package.json`, `pnpm-lock.yaml`, workspace/root scripts, migration
ordering, and context. Use at most two additional disjoint lanes after the relational vocabulary is
committed:

1. Repository-contract lane: only `packages/control-plane/src/repositories/**` and its focused
   type/unit tests.
2. Constraint-test lane: only `packages/control-plane/tests/**`, based on the committed migration
   and repository APIs.

The integration owner alone edits migrations, package metadata, lockfiles, and shared context, then
integrates in this order:

1. Package scaffold + migration vocabulary/SQL.
2. Repository interfaces + typed results.
3. PGlite migration/constraint/repository contract tests.
4. Root verification command integration and handoff.

Small serial commits are preferred inside the task, but the final handoff must leave one clean,
fully integrated `main` history. Do not let agents independently regenerate the lockfile or edit the
same migration.

## Explicitly out of scope

- Neon project/branch creation or network access.
- A production Neon/Cloudflare database driver or repository implementation.
- Better Auth, Google OAuth, R2, Cloudflare Worker/Workflow bindings, or deployment.
- API route changes, durable UI claims, fixture/local state replacement, provider transports.
- Provider credentials, RunPod/Runware calls, model benchmarks, or gate closure.
- Destructive/down migrations. Rollback is a Git revert before external application; later applied
  schemas move forward through additive corrective migrations.
