## Design

1. Reuse Postgres and existing Workflows. Serialize a small durable provider gate before each paid claim. Store only non-secret provider identity, policy, wait order and cooldown. No new queue service or in-memory-only global counter.
2. Separate provider rate, outstanding-task capacity and per-video limits. Kie gets account-wide start pacing. Fal keeps its provider queue with bounded application backlog. Runware uses appropriate model lanes rather than pretending it has a universal published concurrency limit. J1TTS gets narration concurrency and generation rate matching the actual subscription.
3. Order waiting work fairly across accounts. Recheck ownership, cancellation and original job eligibility inside the claim transaction. Do not hold transactions during network calls. Continue status/result observation even when submission capacity is unavailable.
4. Distinguish confirmed rejection from uncertainty. Only documented, positively unaccepted throttles can release a submission claim. Persist an exact claim-fenced rejection receipt and a bounded Retry-After/backoff deadline. Never reset timeout, malformed acknowledgment, missing ID, 5xx or failed ID persistence into a fresh paid attempt.
5. Keep waiting/cooldown durable across Worker restarts. Queued work has truthful nonterminal progress. Cancelled unsent work produces zero provider POSTs; submitted and uncertain work retains its existing reconciliation requirements.

## Account pool implementation and operating procedure — 4 October 2026

Account secrets live only in the optional `VIDEOFORGE_API_ACCOUNT_CREDENTIALS_JSON` Worker secret. Its value is an array of objects with `id`, `provider` (`KIE` or `FAL`), `credentialVersion`, and `apiKey`. Existing `KIE_API_KEY` and `FAL_API_KEY` remain the immutable `kie-legacy`/`fal-legacy` v1 accounts. Additional IDs use lower-case letters, digits and hyphens, starting with a letter, up to 64 characters. Do not duplicate a legacy ID or key. `VIDEOFORGE_PROVIDER_ACCOUNT_ROUTING_ENABLED` controls admission to additional accounts; turning it off preserves observation through their stored credentials.

To add an account later, extend that secret array, insert its owner-managed `provider_api_policies` gate (`KIE:<id>` or `FAL:<id>`) and disabled `provider_accounts` row with the matching credential version, verify independent quota, effective prices and credential access, then enable the row after a compatible code deployment. No source changes or fixed pool size are needed. New account gates initially preserve the existing per-account request windows (Kie 100 outstanding with 550 ms starts; Fal 4 outstanding with 250 ms starts). These are application bounds, not promises of provider processing concurrency. Adjust the owner-managed bounds only against current provider allowances and measured queue/execution times.

The database chooses a video's preferred account using available occupancy and least-assigned rotation for ties. Every claimed task pins its actual account and version before a provider POST. Unsent work may spill; accepted, queued and uncertain work cannot change keys. Only an exact confirmed-unaccepted receipt clears a rejected attempt's current route; append-only attempt history remains. Account cooldowns apply to the account that refused the task. Published asset provenance includes its original provider account.

The account catalogue's immutable `routing_available_from` protects preexisting generation requests and regeneration requests from new-account allocation during rollout. Disabled accounts remain readable for their existing tasks. Missing or mismatched credentials pause work; they never trigger a different key or a new paid submission. Retain historical secrets until accepted tasks, uncertain submissions and billing are fully reconciled. Changing a credential identity uses a new account alias; never silently replace a historical version.

The account-aware release with pooling off and all historical credentials retained is the rollback target once pooled tasks exist. Never return to a single-key binary after pooled submissions. The routing catalogue and attempt pins require native backup/PITR; portable metadata export and restore reject a nonlegacy catalogue rather than lose paid-task ownership. Restore provider policies before account identities and reconcile credentials before reopening admission.
